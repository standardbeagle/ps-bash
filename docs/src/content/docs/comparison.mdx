# Comparisons

PsBash gives you bash syntax with PowerShell objects underneath.
This page compares it honestly against every alternative so you can decide what fits your workflow.

## Size and Complexity at a Glance

| | **PsBash** | **Git Bash** | **Cygwin** | **WSL** | **Crescendo** |
|---|---|---|---|---|---|
| **Disk footprint** | One module, or one self-contained package | ~300 MB (MSYS2 runtime) | 1-4 GB (base + packages) | 1-15 GB (full distro) | Module + your wrappers |
| **Install** | `Install-Module PsBash` | Git for Windows installer | Setup wizard, select packages | Windows feature + distro | Per-command XML authoring |
| **Runtime** | PowerShell process | Separate mintty/bash process | Separate bash process | Linux VM (Hyper-V) | PowerShell process |
| **Typed objects** | Yes, always | No (strings) | No (strings) | No (strings) | Yes, if configured |
| **PowerShell integration** | Native -- objects flow into cmdlets | None -- separate shell | None -- separate shell | None -- separate OS | Native |
| **Cross-platform** | Windows, Linux, macOS | Windows only | Windows only | Windows only | Windows, Linux, macOS |
| **PATH conflicts** | None (AllScope aliases) | Shadows system PATH | Shadows system PATH | Filesystem boundary | None |
| **Dependencies** | PowerShell 7.4+ (module); none (standalone shell) | MSYS2, MinGW runtime | POSIX emulation DLLs | Hyper-V, Linux kernel | PowerShell 7+ |

## PsBash vs Bash

You type the same command lines, and the `ps-bash` shell runs the script around them:
functions, arrays, `trap`, `set -e`, `pipefail`, here-docs, process substitution and
background jobs. Behavior is checked against bash 5.2; what still differs is listed
under "When Bash Wins". The main difference is what comes out of the pipeline.

| Task | Bash | PsBash | The PsBash Advantage |
|------|------|--------|---------------------|
| List files | `ls -la` | `ls -la` | Returns `LsEntry` objects with `.Name`, `.SizeBytes`, `.Modified` |
| Find text | `grep -r 'TODO' src/` | `grep -r 'TODO' src/` | Returns `GrepMatch` objects with `.LineNumber`, `.FileName`, `.MatchText` |
| Top CPU processes | `ps aux \| sort -k3 -rn \| head -5` | `ps aux \| sort -k3 -rn \| head -5` | `PsEntry` objects with `.CPU` as a decimal, not a string to parse |
| File sizes | `ls -la \| awk '{print $5}'` | `(ls -la).SizeBytes` | Direct property access replaces awk field extraction |
| JSON queries | `cat f.json \| jq '.name'` | `cat f.json \| jq '.name'` | Works on Windows without installing jq separately |
| Count lines | `wc -l file.txt` | `wc -l file.txt` | `WcResult` with `.Lines`, `.Words`, `.Bytes` as integers |
| Find files | `find . -name '*.ps1'` | `find . -name '*.ps1'` | `FindEntry` objects with `.Path`, `.SizeBytes`, `.IsDirectory` |
| Disk usage | `du -sh src/` | `du -sh src/` | `DuEntry` with `.SizeBytes` as a number, not `4.2M` to parse |
| File info | `stat file.txt` | `stat file.txt` | `StatEntry` with typed `.AccessTime`, `.ModifyTime`, `.SizeBytes` |
| Search (ripgrep) | `rg 'pattern' src/` | `rg 'pattern' src/` | `RgMatch` objects with `.LineNumber`, `.FileName`, `.MatchText` |
| Environment vars | `env \| grep PATH` | `env \| grep PATH` | `EnvEntry` objects with `.Name` and `.Value` properties |
| Directory tree | `tree src/` | `tree src/` | `TreeEntry` objects with `.Path`, `.Depth`, `.IsDirectory` |

### When Bash Wins

ps-bash aims to match bash 5.2 and GNU coreutils. These differences remain:

- **Broken pipes** -- `cmd | head -1` does not send SIGPIPE to the producer. There is
  no exit status 141.
- **Subshells are not processes** -- `( )` and `$( )` run inside the host. `$BASHPID` is
  a synthetic id there, and `ps` knows no such pid.
- **Job control** -- there is no `set -m` job control. `bind` is not a command, because
  the line editor is not readline.
- **Refused options** -- a real GNU option that ps-bash does not implement fails with
  exit 2 and a message.
- **Windows itself** -- no `/bin`, synthesized permission bits, case-insensitive file and
  variable names, `C:/x` paths.
- **System administration on Linux** -- bash is the native shell. PsBash adds a layer.

`set -o pipefail` and `$PIPESTATUS` work: a multi-stage pipeline records each stage's
status. The full list of differences is
[intentional-differences.md](https://github.com/standardbeagle/ps-bash/blob/main/docs/specs/intentional-differences.md).

### What changed in v0.15.0

Three behaviors moved to what bash does. Each can change an existing script:

| Behavior | Before | v0.15.0 (as bash) |
|-----------|--------|-------------------|
| `gci`, `iex`, `r`, `write` in bash code | Ran the PowerShell alias | A function or `PATH` program, else exit 127 |
| `x=1; sh -c 'echo "[$x]"'` | `[1]` | `[]`: a child sees exported variables only |
| `echo "$PWD"` on Windows | `C:\Users\x` | `C:/Users/x` |

Details and what to change:
[Breaking changes in v0.15.0](/ps-bash/getting-started/#breaking-changes-in-v0150).

### When PsBash Wins

- **Typed objects** -- no more `awk '{print $5}'` or `cut -d: -f2` to extract fields. Properties are named and typed.
- **Windows support** -- every command works on Windows, macOS, and Linux without WSL or Cygwin.
- **.NET integration** -- pipe PsBash output into any .NET API or PowerShell cmdlet.
- **No string parsing** -- `(ls -la).SizeBytes` instead of `ls -la | awk '{sum += $5} END {print sum}'`.
- **Pipeline safety** -- objects survive through `grep`, `sort`, `head`, `tail` without losing structure.

## PsBash vs Native PowerShell

In the table below the PsBash form is 34-73% shorter than the native PowerShell form.

| Task | PsBash | Chars | PowerShell | Chars | Saved |
|------|--------|-------|------------|-------|-------|
| List files | `ls -la` | 6 | `Get-ChildItem -Force` | 20 | 70% |
| Find text | `grep -r 'TODO' src/` | 19 | `Get-ChildItem src -Recurse -File \| Select-String TODO` | 53 | 64% |
| Top CPU | `ps aux \| sort -k3 -rn \| head -5` | 31 | `Get-Process \| Sort-Object CPU -Desc \| Select-Object -First 5` | 60 | 48% |
| JSON query | `cat f.json \| jq '.name'` | 23 | `(Get-Content f.json \| ConvertFrom-Json).name` | 44 | 48% |
| First 10 lines | `head -n 10 file.txt` | 19 | `Get-Content file.txt -Head 10` | 29 | 34% |
| Count lines | `wc -l file.txt` | 14 | `(Get-Content file.txt \| Measure-Object -Line).Lines` | 51 | 73% |
| Find files | `find . -name '*.ps1'` | 20 | `Get-ChildItem -Recurse -Filter *.ps1` | 36 | 44% |

### When Native PowerShell Wins

- **Full parameter sets** -- cmdlets like `Get-ChildItem` expose dozens of parameters (`-Depth`, `-Hidden`, `-ReadOnly`, `-Attributes`) that PsBash flags may not cover.
- **PowerShell remoting** -- `Invoke-Command -ComputerName` has no PsBash equivalent.
- **-WhatIf and -Confirm** -- native cmdlets support dry-run and confirmation prompts. PsBash commands execute immediately.
- **Format-\* cmdlets** -- `Format-Table`, `Format-List`, `Format-Wide` give fine-grained output control.
- **Tab completion** -- native cmdlets have richer parameter completion out of the box.
- **Official documentation** -- Microsoft-maintained help for every parameter and example.

### When PsBash Wins

- **Brevity** -- 34-73% fewer characters for the everyday tasks in the table above.
- **Muscle memory** -- if you know bash, you know PsBash. No learning curve.
- **Text pipeline compatibility** -- output looks like bash, so existing scripts and colleagues can read it.
- **Familiar to bash users** -- onboard Linux-native developers to PowerShell without retraining.
- **Consistent flags** -- `-la`, `-r`, `-n` work the way bash users expect.

## PsBash vs WSL

WSL gives you a real Linux kernel. PsBash gives you bash-style commands inside the PowerShell pipeline. They solve different problems.

| Feature | PsBash | WSL |
|---------|--------|-----|
| Platform | Windows, Linux, macOS | Windows only |
| Runtime overhead | None (native PowerShell) | Linux VM with memory allocation |
| Object pipeline | Typed objects (`LsEntry`, `GrepMatch`) | Text strings |
| .NET integration | Full -- pipe into any cmdlet or API | None -- separate OS boundary |
| Real Linux kernel | No | Yes |
| Shell scripting | Bash scripts in the `ps-bash` shell, plus PowerShell | Full bash/zsh scripting |
| File system | Native (no boundary crossing) | `/mnt/c` translation layer |
| Package managers | PowerShell Gallery | apt, yum, pacman |
| System services | PowerShell/Windows services | systemd, cron |
| Network stack | Host network | Bridged or NAT |
| Docker | Docker Desktop | Native Linux Docker |
| Installation | `Install-Module PsBash` | Windows feature + distro download |
| Startup time | A module import, no VM | Seconds (VM boot) |

### When You Need WSL Instead

- **Scripts that need Linux itself**: `/proc`, programs under `/bin`, real permission bits, interactive job control.
- **Docker with Linux containers** or software requiring a Linux kernel.

### Why PsBash Over WSL

- **No VM** -- no 1-15 GB distro, no Hyper-V, no startup delay.
- **Objects flow into PowerShell** -- `ls -la | Where-Object { $_.SizeBytes -gt 1MB }` works natively. WSL output is text you have to parse.
- **No filesystem boundary** -- no `/mnt/c` path translation, no permission mismatches, no line-ending issues.
- **Cross-platform** -- works on macOS and Linux too. WSL is Windows-only.
- **One shell** -- no switching between PowerShell and WSL terminals.

## PsBash vs Git Bash (MSYS2)

Git Bash ships with Git for Windows and gives you a real bash shell with GNU coreutils. It is the most common way Windows developers get `grep`, `sed`, and `awk`. But it is a separate world from PowerShell.

| Feature | PsBash | Git Bash |
|---------|--------|----------|
| Disk size | One module, or one self-contained package | ~300 MB (MSYS2 runtime + coreutils) |
| Output | Typed PowerShell objects | Text strings |
| Shell | Runs inside PowerShell | Separate mintty terminal |
| Pipeline to .NET | `ls -la \| Where-Object { $_.SizeBytes -gt 1MB }` | Not possible -- different process |
| PATH handling | AllScope aliases, no PATH conflicts | Prepends to PATH, can shadow Windows tools |
| Line endings | PowerShell handles natively | MSYS2 translates `\r\n` ↔ `\n` (sometimes wrong) |
| Symlinks | PowerShell API (Developer Mode on Windows) | MSYS2 emulation (sometimes broken) |
| File paths | `C:/Users/...` (drive kept, forward slashes) | `/c/Users/...` POSIX translation |
| Scripting | Bash scripts and PowerShell cmdlets in one process | Real bash scripts, but can't call cmdlets |
| jq built-in | Yes | No (separate install) |
| Commands | 118 | ~80 (GNU coreutils subset) |

### The Fundamental Difference

Git Bash gives you **real GNU coreutils running in a POSIX emulation layer**. The commands are 100% compatible with Linux. But the output is text, the processes are separate, and nothing flows into PowerShell.

PsBash gives you **reimplemented commands running natively in PowerShell**. The output is typed objects. Everything flows into cmdlets, .NET APIs, and PowerShell scripts. But it is a reimplementation, not the real GNU tools.

```powershell
# Git Bash: real grep, but text output, separate process
$ grep -r 'TODO' src/ | awk '{print $1}' | sort -u
# Result: text strings. Can't pipe to PowerShell.

# PsBash: reimplemented grep, but typed objects, native PowerShell
PS> grep -r 'TODO' src/ | ForEach-Object { $_.FileName } | Sort-Object -Unique
# Result: objects. Can pipe to any cmdlet.
```

### When You Need Git Bash Instead

- **Scripts that depend on GNU options ps-bash refuses**, or on MSYS path forms (`/c/Users/...`) in output.
- **You already have it** and just need quick Unix commands outside PowerShell.

### Why PsBash Over Git Bash

- **Objects, not strings** -- `(ls -la | grep '.log').SizeBytes` vs parsing awk output.
- **Stays in PowerShell** -- no context switching, no separate process, objects flow into cmdlets.
- **No PATH conflicts** -- Git Bash prepends MSYS2 to system PATH, shadowing Windows tools. PsBash uses PowerShell-scoped aliases.
- **No line-ending bugs** -- MSYS2's `\r\n` translation corrupts binary files and causes subtle git issues.
- **Cross-platform** -- Git Bash is Windows-only. PsBash works everywhere.

## PsBash vs Cygwin

Cygwin is the heavyweight option: a full POSIX compatibility layer for Windows with hundreds of GNU packages. It has been around since 1995 and provides the most complete Unix-on-Windows experience short of WSL.

| Feature | PsBash | Cygwin |
|---------|--------|--------|
| Disk size | One module, or one self-contained package | 1-4 GB (base + packages) |
| Install process | `Install-Module PsBash` | GUI wizard, select from 2000+ packages |
| Output | Typed PowerShell objects | Text strings |
| Shell | Runs inside PowerShell | Separate bash/zsh in mintty |
| Runtime | Native .NET | `cygwin1.dll` POSIX emulation |
| File paths | `C:/Users/...` (drive kept, forward slashes) | `/cygdrive/c/Users/...` |
| Fork support | N/A (no process forking) | Emulated via `cygwin1.dll` (slow) |
| Package manager | PowerShell Gallery | Cygwin setup.exe (no CLI package manager) |
| Commands | 118 (focused on scripting) | 200+ (full GNU userland) |
| Symlinks | PowerShell API | Cygwin-internal (often broken outside Cygwin) |
| Pipeline to .NET | Native | Not possible |
| Update process | `Update-Module PsBash` | Rerun setup.exe |

### When You Need Cygwin Instead

- **Compiling Linux software on Windows** (gcc, make, autotools).
- **Running legacy scripts** in organizations with decades of Cygwin workflows.

### Why PsBash Over Cygwin

- **No POSIX emulation layer** -- commands are .NET code calling the OS directly.
- **`Install-Module` vs GUI wizard** -- Cygwin's installer has 2000 package checkboxes. PsBash is one command.
- **Drive-letter paths** -- `C:/project/src`, with no `/cygdrive/c/` translation.
- **Objects flow into PowerShell** -- Cygwin is a walled garden. Nothing crosses back.
- **No DLL conflicts** -- `cygwin1.dll` can break other software. PsBash is managed .NET code.
- **No fork penalty** -- Cygwin's fork emulation on Windows is notoriously slow. PsBash runs natively.
- **Updates** -- `Update-Module PsBash` vs re-downloading a 400 MB setup.exe.
- **Cross-platform** -- Cygwin is Windows-only.

```powershell
# Cygwin: path translation headaches
$ find /cygdrive/c/project -name '*.cs' -exec grep -l 'TODO' {} \;
# /cygdrive/c/project/src/Foo.cs  -- Cygwin paths, not Windows paths

# PsBash: native paths, typed objects
PS> find . -name '*.cs' | grep 'TODO' -r
# objects with .FileName and .LineNumber
```

## PsBash vs Windows coreutils (uutils)

Microsoft is bringing a native Unix toolset to Windows by adopting the Rust
[`uutils/coreutils`](https://github.com/uutils/coreutils) — an MIT-licensed reimplementation of
GNU coreutils — so commands like `cat`, `ls`, `cut`, and `sort` ship as real Windows executables.
This is great news, and it solves a **different problem** than PsBash.

The two projects optimize for opposite goals:

| | **Windows coreutils (uutils)** | **PsBash** |
|---|---|---|
| Goal | **Exact GNU compatibility** | **Conceptual compatibility on PowerShell** |
| Unit of compatibility | The single command (byte-for-byte vs GNU) | The whole script (control flow, pipelines, quoting, expansion) |
| Data model | **Text streams** — bytes in, bytes out | **Typed objects** — `LsEntry`, `GrepMatch`, `WcResult` flow through the pipeline |
| What it is | A set of standalone `.exe` binaries | A transpiler + runtime + interactive shell on PowerShell |
| Pipeline | Real OS process pipes between binaries | A PowerShell object pipeline |
| `ls -la \| awk '{print $5}'` | Re-parse text columns, exactly like GNU | `(ls -la).SizeBytes` — the field is already a typed property |
| Runs *as a shell* | No — you still need bash/PowerShell to drive them | Yes — `ps-bash` is an interactive REPL and script runner |
| Best when | You want a drop-in `cat`/`sort`/`cut` that matches GNU output to the byte | You want bash *scripts and sessions* to run on PowerShell with objects underneath |

### Exact text compatibility vs conceptual compatibility

uutils aims to be **the GNU tool**: feed it the same bytes and you get GNU's bytes back, including
the quirks. That is exactly what you want when a Makefile or a CI step shells out to `sort -u` and
depends on its precise text output.

PsBash aims for **conceptual** compatibility. `sort` *means* "order these records"; on PsBash it
orders typed objects and the records keep their structure, so the next stage reads
`.SizeBytes` instead of re-splitting a text column. The bash you write looks the same — the thing
flowing through the pipe is richer.

```powershell
# uutils: real coreutils, text in / text out — matches GNU exactly
PS> uu-ls -la | uu-awk '{print $5}'   # parse column 5 back out of text

# PsBash: same bash surface, but objects underneath
PS> (ls -la).SizeBytes                # the size is already a number
```

### Single command vs script coverage

uutils replaces commands **one at a time**. It does not parse `if`/`for`/`case`, here-docs,
`$(...)` substitution, parameter expansion (`${x:-default}`), brace expansion, `&&`/`||` lists, or
`trap`/`set -e` — those belong to whichever shell invokes the binaries.

PsBash's transpiler covers exactly that layer. The goal is for a **bash script** — not just a lone
command — to run on PowerShell:

```bash
# A script, not a single command. PsBash transpiles the whole thing.
set -euo pipefail
for f in *.log; do
  count=$(grep -c ERROR "$f")
  if [ "$count" -gt 0 ]; then
    echo "${f}: ${count} errors"
  fi
done | sort -t: -k2 -rn | head -5
```

### Use both

These are complementary, not competing. If Windows ships uutils, you get fast, GNU-exact binaries
for the cases that need byte-for-byte text fidelity — and PsBash can call them like any external
command. Reach for **uutils** when you need a drop-in GNU command with exact text output; reach for
**PsBash** when you want to run bash *scripts and interactive sessions* on PowerShell and keep typed
objects in the pipeline.

## The Bottom Line

PsBash runs bash commands and bash scripts on PowerShell. It does not provide a Linux kernel or Linux programs.

If you need a full Linux environment, use WSL.
If you need deep PowerShell parameter control, use native cmdlets.
If you need byte-exact GNU output for every option, use the GNU tools.

If you need **bash scripts and bash syntax with typed PowerShell objects** on Windows, macOS, and Linux, that is what PsBash does.
