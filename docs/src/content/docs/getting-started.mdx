## Prerequisites

The ps-bash module requires **PowerShell 7.4 or later**. Check your version:

```powershell
$PSVersionTable.PSVersion
```

If you need to install or update PowerShell, see the
[official installation guide](https://learn.microsoft.com/en-us/powershell/scripting/install/installing-powershell).

The standalone `ps-bash` shell is self-contained and needs no .NET runtime.

<Aside type="caution" title="Upgrading to v0.15.0?">
Three changes can alter what an existing script does. Read
[Breaking changes in v0.15.0](#breaking-changes-in-v0150) first.
</Aside>

## Installation

<Tabs>
  <TabItem label="PowerShell module">
    Install from the PowerShell Gallery and import it:

    ```powershell
    Install-Module PsBash
    Import-Module PsBash -DisableNameChecking
    ```

    This adds `ls`, `grep`, `awk` and the other commands to your PowerShell session.
  </TabItem>
  <TabItem label="Standalone shell">
    The `ps-bash` binary runs bash scripts and an interactive bash shell.

    <Tabs>
      <TabItem label="Linux / macOS">
        ```bash
        curl -fsSL https://raw.githubusercontent.com/standardbeagle/ps-bash/main/install.sh | bash
        ```
      </TabItem>
      <TabItem label="Windows">
        ```powershell
        iwr https://raw.githubusercontent.com/standardbeagle/ps-bash/main/install.ps1 | iex
        ```
      </TabItem>
    </Tabs>

    Release archives are built for Windows x64, Linux x64 and macOS arm64. Then:

    ```bash
    ps-bash -c 'ls -la | grep .md'   # one command
    ps-bash script.sh                # a script file
    ps-bash                          # an interactive shell
    ```
  </TabItem>
  <TabItem label="Profile auto-load">
    Add the import to your PowerShell profile so ps-bash loads every time you open a terminal:

    ```powershell
    Add-Content -Path $PROFILE -Value 'Import-Module PsBash -DisableNameChecking'
    ```

    Restart your terminal or reload the profile:

    ```powershell
    . $PROFILE
    ```
  </TabItem>
</Tabs>

## Verify installation

```powershell
Get-Module PsBash          # Should list the PsBash module
Get-Command ls             # Should show Alias -> Invoke-BashLs
ls --help                  # Should display flag descriptions
```

If `Get-Module` returns nothing, run `Import-Module PsBash -DisableNameChecking` and try again.

## Your first 5 commands

### 1. List files with details

```powershell
ls -la
```

```text
total 12
drwxr-xr-x  5 you you 4096 Apr  2 10:30 .
drwxr-xr-x  3 you you 4096 Apr  1 09:15 ..
-rw-r--r--  1 you you 1084 Apr  2 10:30 README.md
drwxr-xr-x  2 you you 4096 Apr  2 10:28 src
drwxr-xr-x  2 you you 4096 Apr  2 10:29 tests
```

Each row is an `LsEntry` object. You can access its typed properties directly:

```powershell
$files = ls -la
$files[2].Name        # README.md
$files[2].SizeBytes   # 1084
$files[2].Permissions # -rw-r--r--
```

### 2. Pipeline composition

```powershell
cat README.md | grep 'bash' | wc -l
```

```text
3
```

`cat` reads the file, `grep` filters lines containing "bash", and `wc -l` counts the matches. Each stage passes typed objects through the pipeline.

### 3. Find files by pattern

```powershell
find . -name '*.ps1' -type f
```

```text

./tests/PsBash.Tests.ps1
```

## The typed-object difference

Every ps-bash command returns structured PowerShell objects, not plain text. This is the key difference from real bash.

```powershell
$result = ls -la | grep '.ps1'
$result[0].GetType().Name   # PSCustomObject
$result.FileName             # Array of matched file paths
```

Because `grep` returns `GrepMatch` objects, you can access `.FileName`, `.LineNumber`, and `.Line` directly instead of parsing text with `awk` or `cut`.

```powershell
$sizes = ls -la
$sizes.SizeBytes | Measure-Object -Sum -Average

# Count  : 5
# Sum    : 14488
# Average: 2897.6
```

Standard PowerShell cmdlets like `Measure-Object`, `Where-Object`, and `Group-Object` work on the result because the pipeline carries typed data.

## Running bash scripts

The module gives you commands. The `ps-bash` shell runs whole scripts: functions, arrays,
`trap`, `set -e`, `pipefail`, here-docs, process substitution and background jobs.

```bash
#!/usr/bin/env bash
set -euo pipefail

for f in *.log; do
  count=$(grep -c ERROR "$f" || true)
  if [ "$count" -gt 0 ]; then
    echo "${f}: ${count} errors"
  fi
done | sort -t: -k2 -rn | head -5
```

```bash
ps-bash count-errors.sh
```

Behaviour is checked against bash 5.2. Where ps-bash differs on purpose, the difference
is listed in
[intentional-differences.md](https://github.com/standardbeagle/ps-bash/blob/main/docs/specs/intentional-differences.md).

## Breaking changes in v0.15.0

v0.15.0 moves three behaviours to what bash does. Each can change an existing script.

### PowerShell aliases no longer run in bash code

Bash code used to resolve PowerShell's built-in aliases (about 135) before functions and
programs. Now `gci`, `iex`, `r` and `write` behave as in bash: a function or a program on
`PATH` with that name runs, otherwise the command is not found (exit 127). `where` runs
`where.exe`.

```bash
gci            # before: ran Get-ChildItem. Now: gci: command not found (127)
iex 'echo x'   # before: evaluated its argument as PowerShell. Now: not found (127)
```

**What to change:** use the bash command (`ls`) or the full cmdlet name
(`Get-ChildItem`). This applies to the `ps-bash` shell only. Importing the module into
your own PowerShell session leaves that session's aliases alone.

### A child process sees exported variables only

```bash
x=1
sh -c 'echo "[$x]"'    # before: [1]   now: []
export x
sh -c 'echo "[$x]"'    # [1]
```

This holds for nested shells (`sh -c`, `bash script.sh`), programs started with `2>&1`,
`&>` or `|&`, and for `env`, `printenv` and `compgen -e`.

**What to change:** `export NAME`, or pass it for one command with `NAME=v cmd`.

<Aside type="note">
Not covered yet: a program started plainly (`prog args`, with no stderr merge) still
inherits unexported variables.
</Aside>

### Paths use forward slashes on Windows

Every path ps-bash hands a script is `C:/Users/x` instead of `C:\Users\x`. That covers `$PWD`,
`$OLDPWD`, `~`, `$HOME`, `mktemp`, `realpath`, `readlink`, `type`, `which`, `$0` and glob
results. The drive letter stays; ps-bash never prints `/c/Users/x`.

```bash
echo "$PWD"          # before: C:\Users\x\proj   now: C:/Users/x/proj
echo "${PWD##*/}"    # before: the whole path    now: proj
```

**What to change:** a script that matched on `\` in one of these values needs `/`.
Input is unchanged: `C:/x`, `C:\x`, `/c/x` and `/mnt/c/x` name the same file. `PATH`
keeps its Windows form, with `;` between entries.

## Tab completion

Type `ls -` and press **Tab** to cycle through available flags:

```text
-l   -a   -A   -h   -r   -R   -S   -t   -1   --help
```

All ps-bash commands register argument completers, so your shell suggests valid flags as you type.

## Troubleshooting

**"gci: command not found" after upgrading to v0.15.0**

Bash code no longer resolves PowerShell aliases. See
[Breaking changes in v0.15.0](#breaking-changes-in-v0150).

**"ls still shows native output"**

The module is not loaded, or it was loaded after your shell already resolved `ls` as a native alias. Run:

```powershell
Import-Module PsBash -DisableNameChecking -Force
```

If your shell has a built-in `ls` alias, remove it first:

```powershell
Remove-Alias ls -Force -ErrorAction SilentlyContinue
Import-Module PsBash -DisableNameChecking -Force
```

**"Execution policy error"**

On Windows, you may need to allow script execution:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
```

**"Alias conflicts with existing commands"**

If another module defines the same alias, remove the conflict and reimport:

```powershell
Remove-Alias ls -Force -ErrorAction SilentlyContinue
Remove-Alias cat -Force -ErrorAction SilentlyContinue
Import-Module PsBash -DisableNameChecking -Force
```

To make this permanent, add the remove-and-import sequence to your `$PROFILE`.
