`ls` is a binary cmdlet, `Invoke-BashLs` (`src/PsBash.Cmdlets/InvokeBashLsCommand.cs`). This page explains why it does not use `Get-ChildItem` for files, the order in which it resolves a target, and how to register a custom provider for paths that are not on disk.

## Why not Get-ChildItem

The first `ls` was a psm1 function built on `Get-ChildItem` and `Get-Acl`. It had three problems with bash compatibility:

- **ACL calls on every entry.** `Get-Acl` per file was slow on large directories, and it failed on files with Windows reserved device names (`nul`, `con`, `prn`, `aux`, `com1`–`com9`, `lpt1`–`lpt9`), which Win32 resolves as devices.
- **Directories first.** The listing grouped directories before files. Bash `ls` sorts all entries together.
- **Provider overhead.** Each item went through the PowerShell provider layer and its extra properties.

The cmdlet reads the filesystem directly through `System.IO` and calls PowerShell only for paths that are not on disk.

## Resolution order

For each operand, `Invoke-BashLs` tries:

```
1. Null device (Windows)
   └─ /dev/null lists as a character device, never as C:\dev\null
2. Real filesystem
   └─ Directory.Exists / File.Exists → DirectoryInfo.EnumerateFileSystemInfos
3. Custom providers (Register-BashLsProvider)
   └─ the first provider whose Detect block returns $true
4. PowerShell provider fallback
   └─ Get-Item / Get-ChildItem for Registry:, Cert:, custom PSDrives
```

Steps 3 and 4 run in the psm1 function `Get-BashLsProviderEntries`, because they need module-scoped state the binary cmdlet cannot reach. It returns raw `PsBash.LsEntry` objects. The cmdlet then sorts and formats entries from every step the same way.

<Aside type="note">
A custom provider is only asked about a target that is not a real file or directory. It cannot override a path that exists on disk.
</Aside>

### Real filesystem

- **No ACL calls.** File attributes come from `FileSystemInfo.Attributes`, which the directory enumeration already returned.
- **Reserved names work.** The enumeration lists `nul`, `con` and the rest as ordinary files.
- **Hidden files.** Without `-a`/`-A`, names starting with `.` are skipped, and on Windows so are files with the `Hidden` attribute.
- **Permissions on Windows** come from `FileAttributes.ReadOnly` and the file extension (`.exe`, `.bat`, `.cmd`, `.ps1`, `.sh`, `.com`). See [Cross-Platform Guide](/ps-bash/reference/cross-platform/#file-permissions).
- **Names are shell paths.** An operand is displayed as you typed it. Paths ps-bash builds use forward slashes on Windows.

### Sorting

Every step sorts the same way: all entries together, compared with `StringComparer.OrdinalIgnoreCase` (`a.txt`, `B.txt`, `c/`). `-t`, `-S`, `-X`, `-U` and `-r` change the key or order as in GNU `ls`. GNU `ls` in a UTF-8 locale uses locale collation, so names that start with punctuation can sort differently there.

### PowerShell provider fallback

When the target is neither on disk nor claimed by a custom provider, `Get-BashLsProviderEntries` calls `Get-Item` and, for a container, `Get-ChildItem`. Each item becomes a `PsBash.LsEntry` through `Get-LsEntryFromPsItem`. These entries have read-only permissions (`dr-xr-xr-x` or `-r--r--r--`), no owner or group, and a size only when the item has a `Length`.

A target that resolves nowhere prints `ls: cannot access 'NAME': No such file or directory` and sets exit status 2.

## Bash compatibility

| Behavior | bash | ps-bash |
|----------|------|---------|
| Sort order | all entries together | all entries together, case-insensitive ordinal |
| Trailing `/` on dirs | only with `-p` / `-F` | only with `-p` / `-F` |
| `nul` in a directory | listed | listed |
| `-a` (show hidden) | `.`-prefixed files | `.`-prefixed files, plus `Hidden` files on Windows |
| `-R` (recursive) | all depths | all depths, symlinks not followed |
| `-l` (long format) | permissions, owner, size | permissions, owner, size |

## Registering a custom provider

`Register-BashLsProvider` is exported by the `PsBash` module. Call it from PowerShell after `Import-Module PsBash`.

```powershell
Register-BashLsProvider -Name 'MyProvider' -Detect {
    param($path)
    $path -like 'MyScheme:*'
} -List {
    param($path, $flags)
    # $flags.Hidden, $flags.Recursive, $flags.Long
    [PSCustomObject]@{
        PSTypeName   = 'PsBash.LsEntry'
        Name         = 'example'
        FullPath     = "$path/example"
        IsDirectory  = $false
        IsSymlink    = $false
        SizeBytes    = 1024
        Permissions  = '-rw-r--r--'
        LinkCount    = 1
        Owner        = 'user'
        Group        = 'group'
        LastModified = [DateTime]::Now
        BashText     = ''  # ls formats the line
    }
}
```

The `List` block receives:

| Parameter | Type | Description |
|-----------|------|-------------|
| `$path` | `string` | The target passed to `ls` |
| `$flags` | `hashtable` | `Hidden` (`-a`/`-A`), `Recursive` (`-R`), `Long` (always `$false`) |

Return `PsBash.LsEntry` objects. `ls` fills in `BashText` and applies its own sort and long format, so the provider does not need to read `-l`, `-t` or `-S`.

Providers are kept in the module-scoped list `$script:BashLsProviders`. To remove one, run the removal inside the module's scope:

```powershell
& (Get-Module PsBash) { [void]$script:BashLsProviders.RemoveAll({ param($p) $p.Name -eq 'MyProvider' }) }
```

## `Get-LsEntryFromFsi` and `Get-BashFileInfo`

The psm1 still defines `Get-LsEntryFromFsi`, which builds a `PsBash.LsEntry` from a `System.IO.FileSystemInfo`, and `Get-BashFileInfo`, a wrapper that calls it. `ls`, `find` and `stat` are binary cmdlets and no longer call either; each has its own C# copy of the logic.
