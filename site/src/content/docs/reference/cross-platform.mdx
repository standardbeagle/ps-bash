A script runs with the same syntax on Windows, Linux and macOS. The commands read different OS
sources on each platform. This page lists where the results differ.

---

## Supported targets

Release archives are built for `win-x64`, `linux-x64` and `osx-arm64`. `install.sh` refuses any
other platform. The PowerShell module (PSGallery / NuGet) runs wherever PowerShell 7.4+ runs.

The code also handles Linux arm64 and musl. Their `struct stat` and termios layouts are defined,
but no release archive is built for them.

### Where OS facts live

OS- and architecture-dependent facts are defined in one place, `src/PsBash.Transpiler/Platform/`.
Commands call these primitives instead of hard-coding a value:

| Primitive | Owns |
|-----------|------|
| `OsSignals` | signal numbers, wait-status decoding, the signal the .NET runtime owns |
| `PosixStat` | `stat`/`lstat`/`fstat` and the `struct stat` layout per OS and architecture |
| `SystemTools` | paths to the OS's own `stat`, `id`, `ps`, `sysctl`, `getent`, and `/bin/sh` |
| `ProcessInfo` | parent pid, zombie state, process-group members, real uid, umask |
| `TerminalIoctl`, `TermiosLayout` | the window-size `ioctl` and termios offsets |
| `UnixSocketPath` | the AF_UNIX path budget: 103 bytes on macOS, 107 on Linux and Windows |

Guard tests fail the build when a signal number, a `struct stat` offset or a hard-coded system tool
path appears anywhere else. The design is in `docs/specs/platform-dependencies.md`.

## Paths

### What a script sees

On Windows every path ps-bash hands back to a script uses forward slashes and a drive letter:
`C:/Users/me/src`. That covers `$PWD`, `$OLDPWD`, `$HOME`, `~`, `pwd`, `mktemp`, `realpath`,
`readlink -f`, `which`, `type`, glob results, the file names `grep` and `find` print, and `<(cmd)`.

`$PATH` is the exception. It stays in Windows form with `;` separators, because native programs
read it.

### What a script may pass

Path operands are accepted in any of these forms:

| Form | Example |
|------|---------|
| Drive, forward slash | `C:/Users/me` |
| Drive, backslash | `C:\Users\me` |
| MSYS / Git Bash | `/c/Users/me` |
| WSL | `/mnt/c/Users/me` |
| Temp directory | `/tmp/x` (mapped to `%TEMP%\x`) |
| UNC | `//server/share/x` |

Device names such as `/dev/null`, `/dev/stdout`, `/dev/stderr` and `/dev/fd/N` are recognised on
every platform and are never opened as files.

### Logical and physical directory

`cd` follows bash: it resolves a relative target, `CDPATH` and `cd -` against the logical `$PWD`,
which is the path you typed with its symlinks left in place. On macOS, `/var` and `/tmp` are links into
`/private`. After `cd "$(mktemp -d)"; cd sub`, `pwd` prints the `/var/...` path, as bash does.

`pwd -P` resolves every link and prints the physical path. `readlink -f` and `realpath` follow
links one component at a time, the way GNU coreutils does.

## File permissions

`ls -l` and `stat` print Unix permission strings (`rwxr-xr-x`) on every platform. The source differs.

<Tabs>
<TabItem label="Linux / macOS">

The mode is the real kernel mode, read through .NET's `UnixFileMode`. Owner and group names come
from the OS `stat` tool, found through `SystemTools`:

| Tool call | Linux | macOS |
|-----------|-------|-------|
| `stat` owner/group | `stat -c '%U %G'` | `stat -f '%Su %Sg'` |
| `stat` inode/blocks/device | `stat -c '%i %b %d'` | `stat -f '%i %b %d'` |
| `ls -l` columns | `stat -c '%h %u %g %f %U %G'` | `stat -f '%l %u %g %p %Su %Sg'` |

</TabItem>
<TabItem label="Windows">

Windows has no POSIX mode bits. The permission string is derived from two facts:

- **Write:** the `ReadOnly` attribute clears `w`.
- **Execute:** a directory, or a file ending in `.exe`, `.bat`, `.cmd`, `.ps1`, `.sh` or `.com`, gets `x`.

Group and other get `r-x` or `r--`. Owner and group are both `%USERNAME%`. ACLs are not read.

</TabItem>
</Tabs>

### stat format specifiers

| Specifier | Meaning | Linux / macOS | Windows |
|-----------|---------|---------------|---------|
| `%s` | Size in bytes | exact | exact |
| `%a`, `%A` | Mode (octal, string) | real mode | from `ReadOnly` + extension |
| `%n` | File name | exact | exact |
| `%U`, `%G` | Owner, group | real | `%USERNAME%` |
| `%i` | Inode | real | `0` |
| `%b` | Blocks | real | `ceil(size / 512)` |
| `%d` | Device | real | drive letter (`C:` = 2, `D:` = 3) |
| `%Y` | Mtime (epoch) | exact | exact |
| `%h` | Hard links | `1` | `1` |

<Aside type="caution">
`stat %h` reports `1` on every platform. `ls -l` shows the real hard-link count, including the NTFS
link count on Windows.
</Aside>

## Process listing (ps)

`ps` returns the same columns (`PID`, `PPID`, `User`, `TTY`, `Stat`, `Command`, …) everywhere.

<Tabs>
<TabItem label="Linux">

`ps` reads `/proc` directly:

| Data | Source |
|------|--------|
| PID, PPID, state, CPU ticks, RSS | `/proc/[pid]/stat` (RSS scaled by the kernel page size) |
| User | UID from `/proc/[pid]/status`, resolved with `getent passwd` |
| Command line | `/proc/[pid]/cmdline` |
| Total memory | `/proc/meminfo` |
| TTY | decoded from `tty_nr` (`pts/0`, `tty1`) |

`Stat` is the kernel's state character (`S`, `R`, `D`, `Z`, …).

</TabItem>
<TabItem label="Windows">

`ps` uses `System.Diagnostics.Process` plus one `Win32_Process` CIM query for the command line,
parent PID and owner. TTY is the session ID as `con<N>`. `Stat` is inferred: `Sl` for a
multi-threaded process, `S` otherwise.

</TabItem>
<TabItem label="macOS">

`ps` uses `System.Diagnostics.Process` plus the OS `ps -axo pid=,user=,ppid=,tty=` for user, parent
PID and TTY. Total memory comes from `sysctl -n hw.memsize`.

</TabItem>
</Tabs>

## Signals

Every signal number a script sees uses Linux numbering, on every OS: `kill -l`, `trap ... USR1`,
`kill -10`, and the `128+N` status of a child killed by a signal. ps-bash converts to the native
number only at the OS call.

<Aside type="caution" title="SIGUSR1 on macOS">
On macOS the .NET runtime uses SIGUSR1 internally, so ps-bash never registers it. A SIGUSR1 sent
from outside ps-bash does not reach `trap ... USR1`. `kill -USR1` sent from a ps-bash shell does.
SIGUSR2 is caught on every platform.
</Aside>

## System tools

On Linux and macOS, ps-bash calls the OS's own `stat`, `id`, `ps`, `sysctl` and `getent` when .NET
cannot answer. `SystemTools` looks in `/usr/bin`, `/bin`, `/usr/sbin` and `/sbin` before `$PATH`,
so a different `stat` earlier on `$PATH` (Homebrew's GNU coreutils on macOS, for example) is not
picked up with the wrong flag dialect.

Windows has none of these tools. The data comes from .NET and CIM.

## Symlinks (ln -s)

<Tabs>
<TabItem label="Linux / macOS">

Symbolic and hard links work without restrictions:

```bash
ln -s target linkname        # symbolic link
ln target linkname           # hard link
ln -sf target linkname       # replace an existing link
```

</TabItem>
<TabItem label="Windows">

Creating a symbolic link needs **Developer Mode** (Settings > System > For developers) or an
elevated shell. Without either, `ln -s` fails with `ln: failed to create symbolic link`.

A hard link needs no elevation, but the target must be a file on the same NTFS volume.

</TabItem>
</Tabs>

## CI matrix

`.github/workflows/ci.yml` runs the Pester suite on `windows-latest`, `ubuntu-latest` and
`macos-latest` on pushes and pull requests to `main` (Markdown-only changes are skipped). The
release workflow, `publish.yml`, runs Pester and the Core, Cmdlets, Host and Differential xUnit
suites on all three OSes, and publishes nothing unless they pass. The macOS Cmdlets suite is
advisory for now. Tests that depend on the OS use Pester's `-Skip:` with
`$IsWindows`, `$IsMacOS` and `$IsLinux`.
